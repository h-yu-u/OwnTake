# OwnTake 分阶段实施计划

> 状态：P0 设计基线与 P1–P5 代码已实现；各阶段分别创建 PR，并在自动检查成功后合入 main。各阶段分别记录代码验证与外部环境验收，未执行的目标 Mac / 真实模型检查不算通过。P3 真实账户验收仍待可用凭据，当前以离线故障契约与真实媒体输出验证代码。
>
> 关联：[产品需求](product-design.md) · [技术架构](architecture.md) · [原型说明](prototype/README.md)

## 1. 实施原则

先完成一条能运行的本地创作流程，再扩大模型和编辑能力。P1 就能通过导入素材导出短片，P2 让分镜规划和可选推理连接可用，P3 接上真实图片/视频模型并扩展异步生成与恢复语义，形成自用 MVP。P4、P5 根据实际使用反馈选择，不是交付首版的前提。

可靠性随对应能力一起实现：P1 的本地文件与渲染必须可恢复；P2 接入外部计费推理时，就有调用审计、请求次数/费用上限和响应未知不盲重试；P3 再补齐异步图片/视频生成的费用预留、远端任务恢复与下载入库。不能先做一个会重复付费的调用按钮，再把恢复排到“优化阶段”。

阶段可以拆成多次小提交。每次提交应围绕一个可观察结果，例如“导入文件后能看到媒体信息”或“响应丢失时不会再次提交”。不为未来多用户需求增加服务、数据库或消息系统。

## 2. 阶段总览

| 阶段 | 目标 | 用户可用结果 | 进入下一阶段的条件 | 详细计划 |
| --- | --- | --- | --- | --- |
| P0 | 明确范围、界面与合同 | 可点击原型、PRD、架构、阶段文档 | 需求/状态/术语一致，原型流程可演示 | [00 · 设计基线](phases/00-design.md) |
| P1 | 建立本地创作底座 | 导入素材，排列片段，导出本地 MP4 | 项目与渲染任务可恢复，工具错误可诊断 | [01 · 本地底座](phases/01-local-foundation.md) |
| P2 | 完成分镜工作台 | 手动分镜、有界推理草稿、候选和版本管理 | 无模型可继续，草稿应用与版本语义稳定 | [02 · 分镜工作台](phases/02-storyboard.md) |
| P3 | 接通可靠的模型生成 | 图片/视频生成、审核选择、局部修改、基础成片 | 真实模型闭环和异常恢复均验收，完成演示作品 | [03 · 生成闭环与 MVP](phases/03-generation-mvp.md) |
| P4 | 提升创作效率与质量 | 更好剪辑、音频、审核；可选 CC/Codex | 扩展保持项目格式与执行边界兼容 | [04 · 编辑与运行时](phases/04-editing-and-runtimes.md) |
| P5 | 根据需要封装桌面入口 | 可选 Electron 启动器与任务生命周期管理 | 浏览器与桌面入口共享同一核心和项目 | [05 · 可选桌面端](phases/05-optional-desktop.md) |
| P6 | 全局故事资产 | 故事、结构与剧本不可变版本，可由有权使用的故事创建作品 | 版本隔离、链接归属与迁移备份通过检查 | [06 · 故事库](phases/06-story-library.md) |
| P7 | 外部发现与来源 | 授权知乎检索、小红书域名过滤、手动来源收藏 | 正文与版权隔离、无凭据时仍可使用本地故事 | [07 · 外部发现](phases/07-story-discovery.md) |
| P8 | 全局人物资产 | 锁定人物参考图、造型、声音预设，跨作品复用 | 人物视觉版本不可覆写、备份包含全局图片 | [08 · 人物库](phases/08-character-library.md) |
| P9 | 剧本与人物生成闭环 | 剧本转可审阅草稿、镜头绑定、参考图模型适配 | 引用不静默删除，生成输入、预算和演员版本冻结 | [09 · 人物驱动影片](phases/09-cast-driven-filmmaking.md) |

依赖顺序为 P0 → P1 → P2 → P3，扩展阶段为 P6 → P7 → P8 → P9。P3 完成后，可以持续使用 Web 版本。P4 的不同增强可独立选择；P5 依赖稳定的本地核心，不要求先完成 P4 的所有功能。

## 3. 建议代码组织

下列目录表达实施边界；已创建模块以仓库代码及各阶段验证记录为准。

```text
apps/web/                 Vue 3 + TypeScript + Vite 界面
apps/server/              Node.js 本地 API、静态资源、SSE、生命周期
packages/domain/          领域对象、版本、状态归约器、依赖规则
packages/storage/         SQLite schema、迁移、事务与本地文件登记
packages/providers/       能力清单、验证、编译与真实供应商适配
packages/runtimes/         有界原生任务循环，可选外部 Agent 运行时
packages/media/           ffprobe/FFmpeg、时间线编译、导出
packages/contracts/       边界 schema、错误码和不含凭据的共享类型
fixtures/                 小型许可明确的演示媒体与故障场景
docs/                     设计、阶段计划与原型
```

这些目录表达代码边界，不要求做成独立部署服务。首版仍是一个本地 Node 服务，按需启动 CLI/媒体子进程。SQLite、文件、任务和外部请求的细节遵循[架构文档](architecture.md)。

## 5. MVP 的统一完成定义

P3 不以“按钮能调用一次接口”作为完成标准。以下条件全部满足后，才将版本标记为可日常使用的 MVP：

- 能从新项目开始制作并导出一部混合素材短片，不需要手动修改数据库或执行内部脚本。
- 首个真实图片连接和视频连接均有记录过的能力验证；不支持的输入组合在提交前被拦截。
- 生成计划、模型连接、输入版本、费用预留与操作标识在外部提交前持久化。
- 浏览器重开、本地服务重启、已知远端任务继续运行和下载中断有可验证的恢复路径。
- `submission_unknown` 不自动重新提交；用户可以核对已知任务或明确保留为待处理。
- 素材版本、审核、当前选用版本和时间线之间能追溯；旧任务不会把新镜头要求标记完成。
- 字幕和音量的局部修改不会重新生成画面；变化后的导出引用正确的新版本。
- 本地路径限制、凭据隔离、脱敏日志和一致性备份在对应功能上有效。
- 原型中的模拟文案不会进入正式运行路径；实际错误、未知费用和未检查项目如实显示。

## 6. 验证策略

测试只覆盖存在明确风险的行为，不用大量镜像实现的测试增加维护负担。

| 层级 | 必须验证的风险 | 验证方式 |
| --- | --- | --- |
| 领域逻辑 | 状态转换、版本失效、预算边界、旧结果归属 | 使用确定输入/事件的单元测试 |
| 存储与任务 | 迁移、恢复、重复事件、原子入库 | 临时 SQLite 与文件目录的集成测试 |
| 适配器 | 真实参数合同、未知提交、取消差异、过期链接 | 模拟故障合同测试 + 少量有预算的真实请求 |
| 媒体 | 引用、时长、画幅、音轨、字幕、输出可播放 | 小型固定素材通过 ffprobe 和人工播放检查 |
| 用户流程 | 新建到导出、能力冲突、版本切换、错误恢复 | 少量端到端场景与真实使用验收 |

付费模型测试不进入每次普通提交的自动回归。默认使用确定性的模拟供应商验证状态与异常；真实调用使用明确的连接、预算与记录。只有验证了真实端点，才把其能力清单标记为已验证。

## 7. 风险与决策时点

| 风险或待定项 | 最晚处理阶段 | 处理方式 |
| --- | --- | --- |
| 目标机器的 FFmpeg、字体与编解码能力 | P1 | 启动健康检查并跑小型媒体样例，不假设交互式 shell 配置可用 |
| 项目移动、素材损坏、磁盘不足 | P1 | 相对引用、完整性状态、重新关联、原子文件写入和恢复流程 |
| 首个推理连接与生成连接 | 分别在 P2/P3 实接前 | 使用用户已有可用账号或端点，先验证能力再接入工作台 |
| 不支持幂等提交的端点 | P2 起，P3 扩展 | 提交歧义进入未知状态，不自动重发；生成任务保留费用预留并人工核对 |
| 价格缺失或随模型变化 | P2 起 | 记录价格依据/时间；没有可信上界时使用用户确认的预留额 |
| 审核模型无法覆盖真实动作与声音 | P3 基础，P4 增强 | 显示实际检查范围，保留人工确认，不伪造通过结果 |
| CC/Codex 的工具、认证和进程差异 | P4 | 独立运行时适配层，先做受限任务，再决定是否进入主流程 |
| 桌面打包带来 Node/FFmpeg 路径问题 | P5 | 核心与外壳分离，打包环境做启动、关闭、恢复验收 |

不提前指定供应商模型版本、价格、开发天数或所有未来功能。每完成一阶段，记录实际使用中的阻塞，再决定下一阶段的最小范围。

## 8. 交付与记录方式

每阶段提交应包含实现、必要迁移、对应使用说明和验收记录。验收记录至少写明版本/提交、机器和工具条件、实际执行场景、结果与已知限制；没有执行过的测试保持“未执行”，不将设计预期写成实测结论。

架构合同发生变化时，先更新[技术架构](architecture.md)和受影响的需求/阶段文档，再实现。阶段任务列表是计划，不自动等同于 GitHub Issues，也不表示已经开展外部调用或付费测试。
